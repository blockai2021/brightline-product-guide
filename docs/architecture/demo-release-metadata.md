# L-014 Demo release metadata

Admin footer and Version & build dialog share one immutable build-info module.
No product, identity, DPP, QR or printing logic is changed.

## Metadata contract

- `VITE_BUILD_ID`: a UUID v4 generated inside the Vite build hook together with its clock; one cached stamp per Vite invocation feeds all bundles. The ID is baked into the bundle and never regenerated by refresh, SSR, copy or language changes. Development/missing build metadata displays Unknown. Rebuilding the same source produces a different ID; redeploying the same built artifact preserves its ID. This is a build identity, not a Git SHA or Deployment ID.

- `VITE_PREVIEW_SESSION_ID` and `VITE_PREVIEW_STARTED_AT`: generated together once in the existing Vite plugin's development config hook, cached for that service invocation, and injected into all development module environments. The UTC time is config initialization at service startup, not browser load time. Reloads, copying and language changes preserve the pair; a service/config restart creates another pair. Neither is persisted in browser storage or shipped in production bundles. Preview hosts show this dedicated pair; localhost Development also shows it when serving these development modules. A built static Preview has build metadata rather than a running development-service session and cannot truthfully invent a session.

- `VITE_APP_GIT_SHA`: full 40-character Git commit SHA, supplied **only by the actual build pipeline** for its source revision. No automatic Lovable SHA variable was verified in this task. Missing/invalid values remain Unknown internally and display localized Unverified; do not set this manually to the latest main commit.
- `VITE_APP_VERSION`: approved product version. Unconfigured fallback `V0.1-demo` is explicitly provisional and pending owner approval; no V1 release is implied.
- `VITE_BUILD_TIME`: when generating Build ID, use the same cached build stamp's UTC clock instead of an independently supplied timestamp. Both values are identical across SSR and browser bundles. Development has no build timestamp. It is not publication time. Timestamps must specify a timezone.
- `VITE_DEPLOY_TIME`: optional actual publication timestamp from the deployment pipeline, otherwise `Unknown`. Never infer it from build time or browser time.
- Environment is a presentation label derived after hydration from the exact site hostname: localhost = Development; Lovable preview host = Preview; the known published app host = Stable Demo; other hosts = Unknown. It is not proof of release approval or commit identity.

Build metadata is frozen in the app bundle. Updating GitHub main without publishing does not update the published bundle's metadata. A verified SHA source can later replace Unknown through CI injection; no runtime GitHub request or git HEAD fallback is allowed.

## Follow-up platform investigation

Official documentation does not document automatic `VITE_APP_GIT_SHA`, `VITE_BUILD_TIME` or `VITE_DEPLOY_TIME` for hosted builds. The Business+ publish API documents a deployment ID, status and URL but not source SHA or actual deployment timestamp, and no automatic app build injection of its ID is documented. The `project.published.v1` event does document `data.published_at`: the UTC time Lovable observed completion, not the build time. No event receiver or publish API integration is connected here, so the app still has no verified deployment ID/time feed. This is a limit of the verified interface, not proof that no internal metadata exists. Local variable absence alone does not establish hosted settings.

Sources: https://docs.lovable.dev/features/secrets#secrets-vs-vite_-environment-variables and https://docs.lovable.dev/api-reference/deploy-domains/publish-project .

Additional verified sources: https://docs.lovable.dev/api-reference/deploy-domains/get-publish-status and https://docs.lovable.dev/api-reference/events/project-published-v1 .

## Final manual release verification

After a release succeeds, open the actual published `/admin`, copy its report and store the **Build ID + build time + site URL** in the release record. Refresh and copy again to verify the pair is unchanged. Attach the publish status/deployment ID if available from an authorized publishing interface, and the completion event's `published_at` if a verified receiver is connected. Otherwise explicitly record Deployment ID/time as Unknown and record the observation time separately. Compare the record's Build ID with the site's copied Build ID on later bug reports; a mismatch means a different build, not necessarily a known Git revision. A Build ID alone does not prove the source SHA or exact deployment timestamp. No GitHub main inference is used.

The Vite helper loads explicit `VITE_` build inputs and injects only selected metadata values plus its generated build/session stamps, never all environment values. Missing SHA and deploy time are not inferred. It does not guess CI variable names.
